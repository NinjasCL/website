# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this project is

`website` is the Gleam source for the **ninjas.cl** site, built with
**blogatto**, a Lustre/mist-based static site generator. The site is fully
implemented:

- `src/site.gleam` — site identity, shared chrome (layout, masthead, navbar,
  footer, icon helpers), and the non-home views: the single post page
  (masthead cover, language options row, machine-translation and staleness
  warnings), the blog index, and the 404 page.
- `src/ninjas/home.gleam` — the home page: hero, marquee, and the about,
  posts, projects, books, games, and banner-wall sections.
- `src/ninjas.gleam` — production build entrypoint; writes the site to `dist/`.
- `src/dev.gleam` — dev-URL build entrypoint (used by the live server).
- `src/ninjas/blog.gleam` — the shared blogatto configuration (posts, feeds,
  sitemap, robots).
- `src/ninjas/local.gleam` — live-reload dev server at `http://127.0.0.1:3000`.
- `src/ninjas/extra_pages.gleam` — writes the root-level `404.html` that
  blogatto's route system cannot express.
- `tools/ftp-upload` — executable Erlang escript that uploads only changed
  `dist/` files to the configured SFTP route via OTP's `ssh_sftp` client.
- `tools/optimize/` — Python 3.14+ / Pillow tool that localizes, optimizes, and
  standardizes blog images; has its own Taskfile and unit tests.

## Commands

```sh
gleam deps download         # Install/update dependencies
gleam run                   # Build the production site into ./dist
gleam run -m dev            # Build with the dev URL (used by the live server)
gleam run -m ninjas/local   # Start the live-reload dev server at http://127.0.0.1:3000
gleam test                  # Run tests
gleam format src test       # Format all source and test files
gleam format --check src test  # Verify formatting (used by CI)
gleam add <package>         # Add a dependency and update gleam.toml

task setup                   # Verify Gleam/Erlang and install dependencies
task build                   # Clean dist/ and build the production site
task optimize                # Localize, optimize, and normalize blog images
task dev                     # Clean dist/ and start the live server
task upload                  # Optimize, build, and upload changed dist/ files over SFTP
```

Aliases: `task s` (setup), `task b` (build), `task o` (optimize), `task d` (dev),
`task u` (upload).

## Conventions

- Write idiomatic, formatted Gleam. Run `gleam format src test` before finishing.
- Put tests in `test/`; test functions must end with `_test`.
- Do not commit `build/` or `dist/` output, `.beam`/`.ez` files, `erl_crash.dump`,
  or a running dev server's output.
- Keep `gleam test` and `gleam format --check src test` passing; these are the exact
  checks CI runs on every push and pull request.
- Prefer small, focused changes over broad refactors mixed with feature work.
- Do not commit `.env` (real credentials) or `.ftp-upload-dist/`; keep `env.txt`
  as an empty template. Never run `task dev` or `task upload` as part of
  verification; they start a long-lived server or deploy to a remote host.
- Files under `static/` are verbatim: do not optimize, resize, rename, or
  rewrite them. Post images are localized under `blog/<slug>/`, optimized once
  per content hash, and tracked in the committed `optimize-manifest.json`.
  Run `task optimize` before building when post images change.

### Deployment tools

- Copy `env.txt` to `.env` and fill in `FTP_USER`, `FTP_PASSWORD`, `FTP_HOST`,
  `FTP_PORT`, and `FTP_ROUTE`. `FTP_ROUTE` is an absolute remote directory.
  `.env` is git-ignored; never commit real credentials. Leave `FTP_PASSWORD`
  empty to use key-based authentication.
- `Taskfile.yml` loads `.env` via its root `dotenv` setting. `task upload`
  (alias `u`) runs `optimize` and then `build` in order, compares the fresh
  `dist/` with the git-ignored `.ftp-upload-dist/` snapshot via
  `git diff --no-index --name-status`, and passes only added/modified/deleted
  paths to `tools/ftp-upload`. The snapshot is refreshed only after a
  successful upload, so failures are retried.
- `tools/ftp-upload` is an executable Erlang escript using OTP's `ssh_sftp`
  client. Keep it executable and keep its stdin contract
  (`A|M|T|D<TAB>relative/path`) in sync with the Taskfile's path normalization.
  It creates missing remote directories, streams files in chunks, overwrites
  existing files, and deletes removed files. Do not replace it with shell-based
  `sftp`/`curl` calls.

### Image optimization

- `tools/optimize/` uses Python 3.14+ and Pillow. Its nested Taskfile installs
  pinned dependencies with `uv`, runs the tool, and runs the Python tests:
  `task -d tools/optimize test`, `task -d tools/optimize check`, and
  `task -d tools/optimize dry-run`.
- The tool downloads remote post images into `blog/<slug>/`, optimizes every
  supported raster image under `blog/` in place, and writes
  `<stem>-1280x720.<ext>` center-cropped cover derivatives. `featured_image`
  points at the derivative; inline images keep the uncropped original. SVG
  covers get a PNG derivative via `resvg-py`.
- `optimize-manifest.json` at the repository root records content hashes,
  downloaded URLs, and cover mappings. Recorded images are skipped; changed
  bytes are optimized again. Keep the manifest committed.

### Blog content

- Posts live one directory per post under `blog/`, written in djot with
  required frontmatter (`title`, `slug`, `date`, `description`).
- `featured_image` frontmatter is the post masthead's cover background on the
  post page and the figure on the home featured row; it defaults to
  `/img/Ninjas.png` when absent. Optimized posts point it at a post-local
  `<stem>-1280x720.<ext>` derivative; the uncropped original stays beside it
  for inline figures. Every post image is served from `blog/`, not an external
  host.
- Language variants are `index-{lang}.djot` files beside the default
  `index.djot`: Spanish (`index.djot`) is human-written and default
  (`language: None`); English (`index-en.djot`), Japanese
  (`index-ja.djot`), and Portuguese (Brazil) (`index-pt.djot`) are machine
  translated. Per the site owner's mandate, EVERY post ships all four
  variants — a post missing any of them is incomplete; the
  `every_post_ships_all_languages_test` enforces it. Variants MUST repeat
  the original's `slug` so the post page groups them into its language
  options row; blogatto routes them to `/blog/{lang}/{slug}/`.
- Non-Spanish variants automatically render the machine-translated warning
  (per-language text in `src/site.gleam`'s language configuration). Posts
  whose `date` is older than 365 days automatically render the staleness
  warning with the elapsed day count. Authors bump `date` when they revise
  a post — it is the last-update date.
- Old posts originally written in English migrate per the site owner's
  rule: the Spanish translation becomes the default `index.djot` (no
  translation warning), and the original English ships as
  `index-en.djot` with the standard machine-translated warning. Convert
  old `*.md.eex` bodies to djot; collapsible `<details>/<summary>`
  toggles become summary-carrying code fences
  (` ```go {summary="Mostrar solución"} `) — raw `=html` fences do NOT
  work, because blogatto wraps every raw block in its own `<div>` and
  the browser closes the `<details>` empty. Copy post-adjacent files
  flat into the post directory (blogatto serves them at the post's URL
  by base name), and preserve the original publication date.
- Fenced code blocks tagged with one of smalto's default languages
  (```go, ```elixir, …) are highlighted at build time: djot blocks reach
  the site's custom content-block component (`src/ninjas/highlight.gleam`),
  which tokenizes via blogatto's public `code.highlight` and renders
  `smalto-*` classed spans styled by `static/style.css`. Untagged blocks
  and unknown language tags render plain.
- The same content-block component renders the old Liquid-tag embeds
  from their fences, each a full OpenGraph card (image, title, text):
  ```` ```github ```` with `owner/repo | description` (a repository
  card linking GitHub, its image the repo's social card), ```` ```ninjas
  ```` with `slug | Post title | description | image` (a card linking
  the site's post with its cover), ```` ```embed ```` with `url | title
  | description | image` (a card for an external website, its site name
  derived from the URL's host), and ```` ```youtube ```` with a URL or
  video id (a full-width embedded player). Convert the old
  `{% github %}`, `{% ninjas %}`, `{% youtube %}`, `{% codeberg %}`,
  `{% devto %}`, and `{% embed %}` tags to these fences; embed fences
  never translate across variants.
- The footer's copyright year is always the build's current year; the home
  page lists default-language posts only.

## OpenSpec 2.0

### How it is installed

- OpenSpec CLI **2.0.0** is available on `PATH`.
- The project uses the `spec-driven` schema, configured in `openspec/config.yaml`
  with project context, per-artifact rules, and apply/archive guidance.
- Workflows are installed as **skills only** in `.agents/skills/`. OpenSpec 2.0
  retired generated slash commands, so there are no `/opsx:*` commands. Invoke a
  workflow by asking for it in natural language or by using the agent's skill tool.
- Each workflow skill also has an OpenCode command wrapper in
  `.opencode/commands/openspec/` (e.g. `/openspec/propose add a post list`). The
  wrappers are thin: they load the matching skill and pass the arguments through,
  so the skills remain the source of truth. If `openspec update` adds, removes, or
  renames skills, update the wrappers to match.
- Skills are generated files. Do not edit them by hand; refresh them with
  `openspec update` after upgrading the CLI.
- Commands act on the nearest `openspec/` root. This repo has no external store
  configured, so no `--store` flag is needed.

Installed workflow skills:

| Skill | OpenCode command | Use it when |
| --- | --- | --- |
| `openspec-explore` | `/openspec/explore` | Thinking through an idea or problem before proposing a change |
| `openspec-propose` | `/openspec/propose` | Turning a described feature/fix into a complete change proposal |
| `openspec-apply-change` | `/openspec/apply` | Implementing the tasks in an approved change |
| `openspec-update-change` | `/openspec/update` | Revising an existing change's planning artifacts |
| `openspec-sync-specs` | `/openspec/sync` | Folding delta specs into main specs without archiving |
| `openspec-archive-change` | `/openspec/archive` | Archiving a completed change and updating main specs |

Examples of natural-language invocations:

- "Propose a change to add a paginated post list."
- "Apply the `add-post-list` change."
- "Update the `add-post-list` change: drop the RSS requirement and add pagination."
- "Archive `add-post-list`."

### Directory layout

```text
openspec/
├── config.yaml
├── specs/
│   └── <capability>/spec.md          # Current behavior (source of truth)
└── changes/
    ├── <change-name>/
    │   ├── .openspec.yaml            # Change metadata
    │   ├── proposal.md               # Why and what changes
    │   ├── specs/<capability>/spec.md # Delta spec (ADDED/MODIFIED/REMOVED)
    │   ├── design.md                 # How, when the change needs it
    │   └── tasks.md                  # Implementation checklist
    └── archive/                      # Completed, archived changes
```

- `openspec/specs/` is the committed, current truth. Do not edit it directly for
  new work; describe the change in a change directory and let archive/sync apply it.
- Specs under `openspec/changes/<change>/specs/` are **deltas**, not full specs.
- `design.md` is conditional: create it when the change has non-trivial design
  decisions. Follow the artifact instructions rather than assuming every change
  needs it.

### CLI quick reference

```sh
openspec list                                  # Active changes
openspec list --specs                          # Main specs
openspec list --all --json                     # Machine-readable inventory

openspec context --json                        # Resolved root + project brief
openspec status --change <change> --json       # Artifact completion + next steps
openspec instructions <artifact> --change <change> --json
                                               # Rules/template for one artifact
openspec show <change>                         # Inspect a change
openspec validate <change>                     # Validate one change
openspec validate --all                        # Validate all changes and specs
openspec validate --specs                      # Validate main specs

openspec archive <change>                      # Archive after completion
openspec doctor                                # Check OpenSpec root health
openspec update                                # Refresh generated skills/files
openspec config profile                        # Add optional workflows
```

Use `--json` whenever the output feeds automation or another tool. The artifact
ids for the `spec-driven` schema are `proposal`, `specs`, `design`, and `tasks`;
always confirm with `openspec status --change <change> --json` before writing.

### Example: create and implement a change

1. Describe the change to the agent:

   > Propose a change to add a paginated post list at `/posts`, using blogatto's
   > content loading. Out of scope: RSS feeds and tag pages.

   The `openspec-propose` skill creates `proposal.md`, the delta spec, `design.md`
   when needed, and `tasks.md`, then validates the result.

2. Or scaffold manually and let the instructions drive each artifact:

   ```sh
   openspec new change add-post-list
   openspec status --change add-post-list --json
   openspec instructions proposal --change add-post-list --json
   openspec instructions specs --change add-post-list --json
   openspec instructions design --change add-post-list --json
   openspec instructions tasks --change add-post-list --json
   openspec validate add-post-list
   ```

3. Implement it by asking "Apply the `add-post-list` change." The
   `openspec-apply-change` skill works through `tasks.md` in order, keeps code and
   specs consistent, and updates the checklist as tasks complete.

4. Finish and archive:

   ```sh
   gleam format src test
   gleam test
   openspec validate --all
   openspec archive add-post-list
   ```

   Archive moves the change under `openspec/changes/archive/` and applies its delta
   specs to `openspec/specs/`.

### Example delta spec

```markdown
## ADDED Requirements

### Requirement: Paginated post list
The site SHALL render a paginated list of posts at `/posts`.

#### Scenario: First page
- **WHEN** a visitor requests `/posts`
- **THEN** the site returns the newest posts, up to the page size
- **AND** the response includes a link to the next page
```

### Example task list

```markdown
## 1. Content and routing

- [ ] 1.1 Load posts from the blogatto content source
- [ ] 1.2 Add the `/posts` route with pagination parameters
- [ ] 1.3 Render the post list with previous/next links
- [ ] 1.4 Add tests for the first page, a middle page, and the last page

## 2. Verification

- [ ] 2.1 Run `gleam format src test`
- [ ] 2.2 Run `gleam test`
- [ ] 2.3 Run `openspec validate add-post-list`
```

### Project-specific OpenSpec rules

`openspec/config.yaml` defines these constraints for artifacts:

- **Proposal:** keep it to a single site feature or content change; state what is
  out of scope; reference the blogatto/Gleam APIs involved.
- **Design:** cover routing, content files, and templates; justify any new
  dependency and explain why an existing blogatto feature is insufficient.
- **Tasks:** use small, verifiable steps and include the checks
  (`gleam test`, `gleam format --check src test`) needed to close each task.
- **Apply:** run `gleam format src test` and `gleam test` before reporting work
  complete; keep the dev server (`gleam run`) out of committed changes.
- **Archive:** summarize what shipped and any follow-up gaps against the specs.

## Definition of done

Before reporting a coding task complete:

1. `gleam format --check src test` passes.
2. `gleam test` passes.
3. Any OpenSpec artifacts touched validate with `openspec validate --all`.
4. The relevant `tasks.md` items are checked off.
5. Completed changes are archived with `openspec archive <change>`.
